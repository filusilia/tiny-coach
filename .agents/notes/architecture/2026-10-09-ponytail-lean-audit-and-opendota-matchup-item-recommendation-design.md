# Agent Note: Ponytail 极简瘦身审计与 OpenDota 对抗大数据出装推荐架构设计

Status: implemented
Date: 2026-10-09
Class: architecture

## 问题背景与因果机制分析

1. **历史架构演进遗留的前端死代码积聚（因果链）**：
   - 伴随着此前针对设置面板高度整合（`VoiceBroadcastSection.vue`）、十人全景战局大盘重构（`MatchDetailPanel.vue`）以及零伪造原则（AGENTS.md 铁律 8）的落地，部分旧版拆分组件和辅助工具已失去所有引用点：
     - `AiReviewPanel.vue`：AI 复盘要点与双击复制已被完全整合至 `MatchDetailPanel.vue` 内部，形成孤立组件。
     - `VoiceBroadcastBar.vue`：实时教练视图底部的折叠式提醒栏已被设置页面的统一播报矩阵取代，未被任何视图挂载。
     - `GsiSimulator.vue`：本地数据模拟器违反零伪造合规红线，且界面已无任何调试入口。
     - `gsiConfig.ts`：前端浏览器触发 cfg 下载的旧版脚本，现已统一收归 Go 宿主层服务。
     - `OverlayWindow.vue`：无引用的外层包装壳组件，`App.vue` 已经直接懒加载 `OverlayView.vue`。
   - 这 5 个文件共计 726 行死代码，不仅增加了静态代码分析和类型门禁的开销，也容易误导后续开发者以为这些路径仍在生产中工作。
2. **Go 侧图标批量抓取编译阻断（因果链）**：
   - `internal/services/system/system_service.go` 在引入连接池复用改造时，调用了 `context.Background()`，但文件头部缺少 `import "context"`，导致 Go 整个工作区无法通过测试（`go test ./...` 阻断报 `undefined: context`）。
3. **实时战况下的“英雄针对性出装”痛点**：
   - 现有的英雄出装参考主要为静态指引或通用推荐，无法根据当前对局实时监测到的 10 人敌我具体阵容（例如敌方存在高爆发控制、强物理被动闪避、高回复肉盾等）动态生成克制出装方案。
   - 开发者期望通过 Valve GSI 实时监测到的对局信息，接入 OpenDota 开放大数据 API，实现真正具备实战针对性的“动态大数据对抗装备推荐”。

## 决策方案

### 1. 执行 Ponytail 极简清理：安全删除 726 行死代码
- 遵循 Ponytail 资深极简原则（*The best code is the code never written*），彻底删除以下 5 个零引用文件：
  - `frontend/src/views/analysis/AiReviewPanel.vue`
  - `frontend/src/components/coach/VoiceBroadcastBar.vue`
  - `frontend/src/components/coach/GsiSimulator.vue`
  - `frontend/src/services/gsiConfig.ts`
  - `frontend/src/windows/OverlayWindow.vue`
- 修复 `system_service.go` 的 `"context"` 标准库导入。

### 2. OpenDota 接口分析与针对性大数据装备推荐设计

通过深入分析 OpenDota 官方 OpenAPI 规范（`https://api.opendota.com/api`），设计出针对实战 GSI 对局的 **四层协同大数据推荐流水线**：

```
+--------------------------------------------------------------------------------+
|                        Valve GSI (10Hz 本地 HTTP 4444)                          |
|  拿到: my_hero_id (我方英雄), enemy_hero_ids (敌方5英雄), clock_time (比赛时间)   |
+---------------------------------------+----------------------------------------+
                                        |
                                        v
+--------------------------------------------------------------------------------+
|               Go 后端服务层 (PlayerService 单例 + SingleFlight + L1/L2 缓存)    |
+--------------------------------------------------------------------------------+
| 1. 基线物品热度 (GET /api/heroes/{my_hero_id}/itemPopularity)                  |
|    -> 提取 start_game / early_game / mid_game / late_game 购买频次 Top 装备     |
| 2. 敌方克制对抗大数据 (GET /api/heroes/{my_hero_id}/matchups)                   |
|    -> 计算本局中敌方对我胜率压制最强的 TOP 2 威胁英雄                             |
| 3. 对抗特征质变加权 (Counter-Item Rule Matrix)                                  |
|    -> 敌方强控/法爆: 提升 BKB (116) / 林肯 (137) 优先级                         |
|    -> 敌方高闪避/被动: 提升 金箍棒 (135) / 白银之锋 (249) 优先级                   |
|    -> 敌方高回复肉盾: 提升 冰眼 (160) / 否决 (381) / 灵龛 (267) 优先级          |
|    -> 敌方高机动逃生: 提升 紫怨/血棘 (98/250) / 缚灵索 (655) 优先级             |
| 4. 关键装 Timing 胜率分析 (GET /api/scenarios/itemTimings)                      |
|    -> 针对当前发育经济 (GPM/NetWorth)，评估当前核心装产出预期与大数据胜率曲线       |
+---------------------------------------+----------------------------------------+
                                        |
                                        v
+--------------------------------------------------------------------------------+
|           前端呈现 (CoachView 战况看板 / OverlayView 独立置顶悬浮窗)              |
|  -> 56x42 规格物品格、中文名常数兜底、分阶段展示（出门/前期/质变针对/神装）         |
+--------------------------------------------------------------------------------+
```

### 3. 防频控与多级缓存落盘策略
- OpenDota 免费端点存在每分钟约 60 次的调用限制。
- `itemPopularity` 与 `matchups` 为全服历史宏观大数据，单场对局内具有绝对不可变性。
- Go 后端在 GSI 捕获对局英雄事件时执行懒拉取，配合本地文件缓存（`cache/opendota/hero_items_{id}.json`，TTL 为 7 天），单场对局网络请求开销降为 0~1 次。

### 4. 实时教练页 (CoachView) 挂载与响应式战术大盘布局重构
- 遵循开工铁律第 8 条（零伪造原则）与第 11 条（官网 56x42 规格物品格、127 英雄中文名静态常数兜底、深色高对比悬浮卡）：
  - 仅在真实连接游戏且拥有有效实操英雄数据（`battle.connected && battle.heroId > 0`）时挂载 `MatchupRecommendationPanel.vue`。
  - 未接入对局时严守“等待 GSI 接入”真实空态守卫，绝不伪造敌法师或虚假出装。
- 采用 **三层战术指挥中枢 (Tactical Command Center) 响应式栅格布局**：
  1. **顶层战备大盘**：实时 HUD 横贯全宽（生命/魔法/KDA/GPM/XPM/买活警戒/昼夜魔方肉山倒计时/技能槽与 56x42 物品栏）。
  2. **中层装备战略**：`MatchupRecommendationPanel` 横向展开本局敌方高危威胁雷达（Threat Radar）、专属针对性质变装矩阵（Counter Items，联动已拥有背包高亮标记），以及全服大数据分阶段标准出装阶梯（出门/前期/中期/后期）。
  3. **底层战术协同**：宽屏下采用 `grid-cols-1 xl:grid-cols-2` 双栏对称排布：
     - 左栏：AI 实时战术参谋即时问答（Solution Hierarchy 思维链快速研判与 TTS 朗读复读）。
     - 右栏：毫秒级实时战术决策流（神符/魔方/肉山/买活/质变装成型通知流，带独立内嵌滚动容器）。
  - 小屏自适应单列纵向降级，兼顾大屏高密度与小屏易读性。

## 曾考虑的替代方案

### 替代方案 A：在前端直接用 fetch 请求 OpenDota 大数据接口
- **最强理由**：前端直接拿 JSON 就可以在 Vue 组件里计算排序，开发速度极快。
- **为什么不采用**：严重违反开工铁律第 6 条与第 10 条。前端直接请求会暴露调用逻辑，多窗口（主窗口 + 悬浮窗）会并发发出重复请求迅速触发 429 封禁，且无法做跨窗口持久化缓存。

### 替代方案 B：仅使用静态常数推荐，不接入 OpenDota 接口
- **最强理由**：100% 离线，无任何外部网络依赖。
- **为什么不采用**：静态常数无法反映当前天梯版本的实际胜率与装备流派迁移，也无法根据敌方具体英雄的威胁度做动态加权。静态配置应作为无网络时的保底，而非放弃大数据的理由。

### 替代方案 C：将出装推荐面板与决策流单列无脑纵向堆叠
- **最强理由**：代码修改最少，无需重构下半部分栅格。
- **为什么不采用**：出装面板包含 4 阶段物品阶梯，加上 AI 参谋区与告警列表，会导致页面纵向滚动距离过长，战局瞬息万变时玩家需要频繁上下滚动查找关键信息；采用三层双栏大盘使信息层级一目了然，极大提升实战阅读效率。
