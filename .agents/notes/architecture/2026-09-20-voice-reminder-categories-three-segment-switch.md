# 架构决策笔记：语音播放栏三段式开关改造与 9 类战术提醒独立判定

- **日期**：2026-09-20
- **责任 Agent**：Antigravity
- **状态**：已落地 (Implemented)
- **关联需求**：语音播放栏三段式开关改造（支持关闭 / 仅文字播报 / 语音+文字播报，按 9 类战术提醒独立配置）

---

## 一、 背景与因果分析

### 1. 现有方案的痛点与因果机制
在神盾教练以往实现中，战术播报模式（`voice_broadcast_mode`）设计为系统全局单一状态（0: 静音 / 1: 仅屏幕通报 / 2: 语音+屏幕）。这种粗粒度单一开关导致了以下电竞实战冲突：
1. **关键高危提醒与低优信息冲突**：玩家在对局中往往希望“血量危险”、“被控制”或“关键大招就绪”这类生死攸关的信息由 TTS 语音强制提醒，但对于“魔方刷新”、“出装建议”或“蓝量不足”等辅助信息，频繁的语音朗读会严重干扰队友语音连麦与战场声音信息（如敌方跳刀声、隐形声、施法抬手音效）。
2. **缺乏类别独立的粒度控制**：全局静音后，玩家连界面上的文字战术气泡也会被弱化或完全停用；而全局开启语音后，又面临高频报点的“听觉疲劳与信息轰炸”。

### 2. 治理目标
将单一全局语音开关重构为**细分战术提醒三段式开关体系**，覆盖基于 Dota 2 GSI 实战快照可精准裁定的 9 大核心战术场景：
- **血量危险**（`health_percent < 20%`）：默认 语音+文字
- **蓝量不足**（`mana_percent < 15%`）：默认 仅文字
- **被控制**（`stunned / silenced`）：默认 语音+文字
- **技能就绪**（大招/BKB 从 CD 变就绪）：默认 语音+文字
- **神符刷新**（神符刷新前 10s）：默认 语音+文字
- **魔方刷新**（魔方刷新前 10s）：默认 仅文字
- **肉山刷新**（肉山刷新前 60s）：默认 语音+文字
- **死亡复活**（`alive == false`）：默认 语音+文字
- **出装建议**（金钱达阈值）：默认 仅文字

## 二、 核心架构决策与设计

### 1. 强类型数据模型契约
在 `src/types/index.ts` 中定义三段式广播模式枚举 `BroadcastMode` 与 9 类战术场景键 `ReminderCategoryKey`：
```typescript
export type BroadcastMode = 0 | 1 | 2; // 0: 关闭, 1: 仅文字播报, 2: 语音+文字播报

export type ReminderCategoryKey =
  | 'health_critical'
  | 'mana_low'
  | 'under_control'
  | 'ability_ready'
  | 'rune_refresh'
  | 'tormentor_refresh'
  | 'roshan_refresh'
  | 'death_respawn'
  | 'item_suggestion';

export interface ReminderCategoryConfig {
  key: ReminderCategoryKey;
  label: string;
  triggerCondition: string;
  defaultMode: BroadcastMode;
  mode: BroadcastMode;
  description: string;
}
```
在 `AppSettings` 中扩展 `reminder_modes: Record<ReminderCategoryKey, BroadcastMode>`，并对旧版 `voice_broadcast_mode` 保持完全向后兼容。

### 2. UI 交互组件：三段式开关 (ToggleButton 组)
创建专有组件 `ThreeSegmentToggle.vue` 与 `VoiceBroadcastBar.vue`：
- **三段视觉状态映射**：
  - **关闭 (0)**：柔和灰暗底色 + 禁用音量图标，明确标识该类别完全静默；
  - **仅文字 (1)**：电竞青蓝（`dota-cyan`）+ 文本气泡图标，在战术流中生成文字裁定，不触发 TTS 发声，适合连麦排位；
  - **语音+文字 (2)**：神盾金色（`dota-gold`）+ 高保真喇叭图标，文字与 Edge-TTS 神经拟真人声同步触达。
- **交互赋能**：支持一键批量配置（全开语音、全开文字、全静音、重置默认）以及单项试听触发。

### 3. GSI 规则引擎与三档行为闭环
在 `gsiRuleEngine.ts` 与 `GsiSimulator.vue` 中统一执行裁定：
- 接收到 10Hz GSI 状态差分或模拟触发时，先判断对应分类的 `mode`：
  - `mode === 0`: 直接丢弃，不占用 UI 列表，不触发 TTS，彻底节约渲染开销；
  - `mode === 1`: 封装 `CoachAdvice` 追加至实时战术流，静默不发声；
  - `mode === 2`: 追加战术流同时调用 `speechService.speak(...)` 进行电竞黑话规范化发音。

## 三、 曾考虑的替代方案与弃用理由

### 1. 替代方案 A：简单复选框（仅控制“是否语音”）
- **被放弃方案的最强理由**：实现极其简单，只需在每类后面放一个 `checkbox`（勾选发声，不勾不发声）。
- **为何弃用**：无法表达“完全关闭该类事件（连文字也不要）”与“仅需要文字气泡不要声音”的本质区别。在激烈团战中，用户往往只想彻底屏蔽无关提醒（如魔方刷新），而不是只关声音。三段式开关（关闭 / 仅文字 / 语音+文字）是电竞级 HUD 最完备的状态机。

### 2. 替代方案 B：在后端的 Go 中过滤模式后再推送到前端
- **被放弃方案的最强理由**：后端直接不推送事件，可减少 IPC 消息数量与前端事件开销。
- **为何弃用**：
  1. 违背“后端单消费者极速吞吐原始快照、前端管理用户个性化偏好与视图展现”的架构分工原则；
  2. 若将用户的提醒开关下沉到 Go 进程，每次前端配置变动均需进行 IPC 双向同步与锁同步，增加链路复杂度；
  3. 前端需要支持单项模拟测试与离线试听，在前端 Store 统一管理响应式开关体验更佳。

---

## 四、 决策后果与收益

1. **战术听觉减负**：玩家可精确保持“残血/受控/关键大招”开启语音，其余降级为文字或彻底静音，避免关键团战语音干扰。
2. **数据模型向后兼容**：老用户的本地配置平滑迁移，缺失字段自动以规范表格中的 `defaultMode` 兜底。
3. **闭环可测性**：战局模拟器（`GsiSimulator`）与实时 GSI 引擎全面覆盖 9 类真实指标，毫秒级响应。
