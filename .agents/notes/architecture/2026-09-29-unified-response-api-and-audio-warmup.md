# Agent Note: AI 双模统一 (Response API 与纯规则)、语音首字静音缓冲与战术规则约束吸收

Status: implemented
Date: 2026-09-29
Class: architecture

## 问题背景与因果机制分析

1. **AI 模式割裂与过度拆分问题**：
   - 此前系统将 AI 模式生硬地划分为“标准云端 API (`cloud_api`)”、“端侧本地推理 (`local_npu`)”与“纯规则引擎 (`rule_only`)”。
   - 但从通信协议与技术本质上看，本地端侧服务（如本地运行的 Ollama、LMStudio、vLLM、Cherry Studio 等）与远程云端大模型服务（如 DeepSeek、OpenAI、通义千问等），**均完全采用相同的 OpenAI 规范 Response API (即 HTTP POST `/v1/chat/completions`)**。
   - 人为将其划分为“云端”和“端侧”导致前端维护了两套几乎镜像的输入框与状态，用户配置繁琐，违背了“不要为了拆分而拆分”的高聚类原则。

2. **语音播报/试听时第一个字音量偏小因果剖析**：
   - 在本地 MeloTTS 合成音频时，声学模型输出的 WAV 数据从 0ms 瞬间开始就是首字的振幅波形；
   - 现代操作系统音频引擎、驱动层与声卡 DAC 芯片在处于空闲状态时会进入节能省电模式；当播放器发起播放时，硬件与驱动建立连接需要 30ms ~ 80ms 的起振与抗爆音平滑过渡（DAC Warmup / Anti-Pop Ramp-up）；
   - 由于首字（尤其是声母如 sh, d, t 等擦音/塞音）振幅本就较弱，恰好落在硬件增益爬升区间，导致前几十毫秒的声音被物理硬件“吃掉”或削弱，用户主观听感为“第一个字音量明显偏小或吞字”。

3. **现有 AI 战术规则缺乏强制约束（对比 BrightGir/dota-ai-coach）**：
   - 通用大模型在缺乏严格战术约束时，极易产生“无脑建议买新大件（如 BKB/分身斧）”的幻觉，完全忽视玩家当前背包中已有的可用技能、推推、风杖等救命资源；
   - 研读业界优秀的开源项目 `BrightGir/dota-ai-coach`，其设计了极为严密的提示词规则体系，特别是“方案优先级金字塔（Solution Hierarchy）”与“因果推演检验”，能够大幅提升 AI 建议的实用性与专业度。

## 决策方案

1. **AI 架构彻底收敛为统一双模式**：
   - 废除“端侧”与“云端”的人为割裂，AI 模式统一为两大高内聚形态：
     - **【API 模式 (标准通用 Response API)】**：面向所有兼容 OpenAI `/v1` 协议的模型端点。统一配置端点基地址 (`ai_endpoint`)、可选密钥 (`ai_api_key`) 与模型名称 (`ai_model`)，内置“本地 Ollama (11434)”、“云端 DeepSeek”、“本地网关 (23333)”一键预设，支持自适应探测可用模型与连通性测试。对旧配置字段实现无感兼容。
     - **【本地纯规则模式 (Rule Only)】**：零网络开销、零大模型依赖，毫秒级硬编码战略事件触发。

2. **WAV 前置静音缓冲注入机制 (Leading Silence Padding)**：
   - 在 `internal/services/melo_engine.go` 中引入 `addLeadingSilenceToWav` 算法：在合成生成的 PCM 数据前注入约 80ms 的零采样静音数据，并同步更新 WAV 头的 `RIFF` 与 `data` chunk 大小；
   - 80ms 的静音让声卡硬件与系统驱动在极短时间内完成平滑起振，首字音节 100% 完整饱满地发音，彻底根治首字吞音与音量偏小缺陷。

3. **吸纳 `BrightGir/dota-ai-coach` 优秀战术规则约束**：
   - 将其核心的 **方案优先级金字塔 (Solution Hierarchy)** 注入 `ai_service.go` 的战术提示词：
     1. **就绪技能与现有装备优先 (最高优先级)**：在确认手头现有技能/物品无法应对前，**严禁无脑建议购买新装备**；
     2. **即将冷却完毕的技能/装备次之**；
     3. **因果链推演检验**：明确各装备机制边界（如莲花是反弹非阻挡，刃甲是反伤非减伤）；
     4. **输出极度精炼**：回答控制在 1~2 句话直接指导操作，适应高节奏竞技。

## 曾考虑的替代方案

1. **方案 1：在前端合成文本前强行拼接空格或中文逗号“，”**
   - 最强理由：改动只需改一行前端代码。
   - 为什么不用：不同 TTS 引擎对标点符号的处理不确定，有时逗号会导致语调异常升调或声学模型发音停顿过长，且无法精确控制音频毫秒数；直接在后端 WAV PCM 字节流头部注入确定性的 80ms 0 采样是音频工程的最佳实践。

2. **方案 2：继续保留“云端 API”与“本地推理”两个独立设置卡**
   - 最强理由：用户直觉上可能觉得本地与云端是两件事。
   - 为什么不用：本质完全相同，重复维护两套表单既冗余又增加代码复杂度，通过一键预设按钮（“本地 Ollama” / “云端 DeepSeek”）切换端点地址既满足了认知直觉，又保持了底层架构的高度统一。
