# Agent Note: 设置页面重构精简、去过度拆分、紧凑个人账号与本地 AI 功能因果定性

Status: implemented
Date: 2026-09-29
Class: architecture

## 问题背景与因果机制分析

1. **设置页面碎片化与过度拆分（过犹不及）**：
   - 之前为了所谓的“解耦”，将本来较为精炼的系统设置强制拆分为了四大 Tab 卡片（首选项、AI 战术引擎、拟真 TTS 语音、其他选项）。
   - 在组件组织上，甚至出现了 `AiTab.vue` 仅包装 `<AiEngineSection />` 一行代码、`TtsTab.vue` 仅包装 `<TtsEngineSection />` 一行代码的极端过度拆分现象。
   - 用户在配置应用时，需要频繁在四个卡片之间反复切换跳转，每个视图内部垂直空间利用率低、视觉割裂，形成了“为了拆分而拆分、拆的太多了”的交互负担。

2. **TTS 引擎已收敛为唯一离线 MeloTTS，配置项已成冗余**：
   - 后端目前已统一固定并内置了纯本地原生离线 MeloTTS 引擎，不再需要也不存在让用户选择切换其它语音合成引擎（如已废弃的外部 edge-tts 候选）。
   - 用户明确提出“TTS 只有一个，不需要设置了，保留试听在语音提醒矩阵”。原有的专门 TTS 设置面板（`TtsTab`、`TtsEngineSection`）已沦为无意义的配置负担。

3. **个人账号绑定组件垂直留白过大、布局松散**：
   - `PlayerBindingSection.vue` 过去采用了大尺寸图标、多行说明文字、大号头像（48px）、大内边距和多层卡片嵌套结构，纵向占据将近 250px 屏幕空间，严重挤占了首屏对“战术语音提醒矩阵”等核心战术配置的展示。

4. **端侧本地 AI（`local_npu`）可用性因果机制的认知混淆**：
   - 后端 `AiService` 的“端侧本地推理”是通过 OpenAI 兼容 HTTP 协议对接本机运行的 Ollama 服务（默认 `http://127.0.0.1:11434/v1`）。
   - 本项目为保持几十兆极轻发布包与零争抢游戏渲染帧率的底线，**并未在二进制安装包内捆绑数 GB 的本地 LLM 权重与本地推理进程**。
   - 因此：
     - 若用户本机已运行 Ollama 服务（如 `ollama run qwen2.5:1.5b`），端侧本地推理从模型探测、拉取、问答到赛后复盘 **100% 完整可用**；
     - 若用户本机未启动 Ollama，端侧探测与测试会直接报连接 11434 端口失败。
   - 界面上缺乏对这一因果机制的清晰提示，导致用户困惑“端侧本地功能到底是否可用”。

## 决策方案

1. **去过度拆分：收敛整合为两大高内聚核心 Tab**：
   - 废除四级碎片化卡片及无意义的空壳包装文件（`AiTab.vue`、`TtsTab.vue` 等），收敛为两大清晰、高内聚、高密度的顶级标签：
     - **【战术偏好与选手】 (Tactics & Audio)**：聚焦对局战术交互体验，内含极紧凑选手账号绑定栏与战术语音提醒矩阵（9大战略事件三段式控制、音量语速滑动条、试听当前音效）。
     - **【AI 引擎与系统】 (AI & System)**：聚焦技术参数与系统设置，内含 AI 战术推理引擎（云端/本地/规则）、局内悬浮窗 HUD 控制、缓存数据管理与版本合规声明。
   - 彻底移除独立的 TTS 设置入口与 `TtsEngineSection`，收敛至语音提醒矩阵中的【试听当前音效】。

2. **个人账号绑定极致紧凑化设计**：
   - 重构 `PlayerBindingSection.vue` 为精悍紧凑的高密度控制条，垂直高度压缩至 75px 以内：
     - 未绑定时：单行自适应整合，输入框与【绑定】按钮平滑集成；
     - 已绑定时：紧凑选手信息栏（32x32 头像、选手昵称、高对比 Account ID、一键复制、一键同步画像、微型解绑按钮），零冗余垂直留白。

3. **端侧本地 AI 机制说明透明化与引导优化**：
   - 在 `AiEngineSection.vue` 本地推理面板中明确标注其因果依赖机制：“端侧本地推理基于本机已运行的 Ollama 服务 (默认端口 11434)。已安装并启动 Ollama 时可自动探测模型并离线运行；若未安装，推荐选用标准云端 API (如 DeepSeek、通义千问等兼容端点) 或纯规则引擎”。
   - 保留本地连通性测试与模型自动探测功能。

## 曾考虑的替代方案

1. **方案 1：完全打平为单页长页面滚动，取消所有 Tab**
   - 最强理由：代码层级最少，一个页面包含所有设置组件。
   - 为什么不用：战术语音提醒矩阵本身有 9 大事件卡片，单页全部平铺会导致页面垂直滚动过长，用户在寻找悬浮窗或 AI 配置时需要滚动多个屏高；划分为“战术偏好与选手”和“AI 引擎与系统”两个大类，分类界限分明、层级扁平、视口整齐，体验远优于无脑长列表。

2. **方案 2：保留 TTS Tab 但仅展示一个简单的状态卡片**
   - 最强理由：可以保留 TTS 引擎的就绪状态提示。
   - 为什么不用：用户明确指出“TTS 只有一个，不需要设置了，保留试听在语音提醒矩阵”，保留独立 Tab 会继续延续碎片化拆分的坏味道；用户关心的核心只有“发声是否正常”，在战术语音提醒矩阵中直接提供试听按钮是最直观、最符合用户直觉的解法。

## 后果与验证计划

- **收益**：
  - 彻底终结过度拆分，设置页面整洁利落，从 4 个散碎 Tab 简化为 2 个高内聚分区；
  - 个人账号绑定高度紧凑，主屏直接呈现核心语音提醒矩阵；
  - TTS 冗余配置彻底清理，试听功能在语音提醒矩阵中流畅运作；
  - 本地 AI 因果逻辑清晰，用户不再产生疑惑。
- **验证方法**：
  - 执行 `node scripts/verify-agent-notes.cjs` 确保决策笔记合规；
  - 执行 `pnpm --filter frontend build` 验证前端全量构建通过；
  - 运行更新后的测试套件验证紧凑组件渲染与功能契约正常。
